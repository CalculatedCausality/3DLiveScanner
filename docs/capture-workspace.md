# Internal active-capture workspace

## Scope

New modern captures use `files/capture-dataset` instead of writing every frame
through the Documents/shared-storage path. Finished models continue to use the
existing selected library, normally `Documents/3D Live Scanner`. No finished
library is moved. The legacy flavor still defaults to the public working path.

The working directory is persistent app data, not evictable cache. The application
already disables backup. Unfinished captures are removed by uninstall/clear-data;
finish saving to the library for the library's existing retention behavior. The
library hint explains the active-capture location.

Geometry, point density, camera poses, JPEG quality, frame formats, preview fsync
and the native state-last commit protocol are unchanged. The native scanner
library is byte-identical to the preceding parallel-I/O build.

## Selection and recovery

`CaptureWorkspace` checks both the historical public `dataset` directory and the
new private workspace. Existing public captures are selected first. If both
contain pending capture data, resolve the public one first, then the next library
refresh discovers the private one. Selection does not move or delete either.

State files, partially written numbered frames and saved working models prevent
automatic reuse. An inaccessible directory is treated as potentially occupied.
Recoverable committed datasets use the existing native validation before being
offered for finalization; incomplete data is retained for explicit user action.

The selected path stays fixed during capture. It is reconsidered only in the idle
library/recovery flow. Native frame writers retain their original dataset path.
Editor/share scratch uses a separate `cache/scanner-work` directory and scoped
FileProvider path. Thumbnails stage beside their destination so their final rename
does not cross filesystems; screenshot sharing includes explicit URI read grants.

## Publication

OBJ/PLY model export already stages resources beside the final library directory.
Raw-dataset save/recovery now uses `IO.publishDirectoryChecked` rather than trying
to rename the private workspace into shared storage:

1. Snapshot the quiescent source tree; reject symlinks/unsupported entries.
2. Copy into a unique staging directory inside the destination library.
3. Flush/sync each file, read it back, and compare length and SHA-256 with the
   streamed source bytes.
4. Check that the source inventory, sizes and modification times stayed stable.
5. Publish through a same-filesystem directory rename, refusing existing targets.
6. Only the successful caller may release the source capture.

Copy, verification, collision or publication failure preserves the source.
Publication followed by a process interruption before cleanup can leave a second
recoverable working copy; it does not justify deleting the only known source.
This is not a whole-directory power-loss-atomic protocol. Finalization needs space
for a staged copy and can take longer than the old same-filesystem rename.

Raw dataset publication retains preview records rather than removing them after
save, so the published dataset keeps the data used by validation/history recovery.
Consequently raw datasets can occupy more space; normal OBJ/PLY publication copies
the model and referenced resources as before.

### On-phone synthetic probe

`tests/capture_io/app_workspace_probe.py` runs generated byte payloads only. It
does not install/restart the scanner or open any captured images. It exercises
production selection/publication code and Java I/O with one joined image writer,
preview fsync and state-last publication. Each timing sequence has 16 frames:
95,136 image-payload bytes, 1,312,004 preview bytes and 147,460 cloud bytes per
frame, plus small pose/timestamp/state files. No JPEG encoding, reconstruction,
GL work or real dataset validation is included.

| Process and storage | Mean ms/frame, run 1 | Mean ms/frame, run 2 |
| --- | ---: | ---: |
| App UID 10467, private files | 7.973 | 6.480 |
| Shell UID 2000, direct `/data/local/tmp` | 7.743 | 5.907 |
| Shell UID 2000, shared Documents storage | 81.022 | 105.565 |

The shell comparison ran shared/direct/direct/shared to control ordering. These
results support investigating the workspace change, not an application-FPS claim.
The `run-as` subprocess has the app UID but cannot create the shared-library
scratch directory in its storage view. That comparison was explicitly skipped;
permissions were not changed. The app-UID private checks and same-filesystem
publication succeeded. A separate shell-UID cross-filesystem test successfully
copied, verified and published the generated fixture while retaining its source.
The probe cleans up its generated dex and uniquely named synthetic directories.

The original strict app-UID-only probe failed at shared scratch creation and
produced an AndroidRuntime message in its own helper process. The scanner process
remained alive. The runner now reports that limitation and separates UID results.

The same log exposed a separate hard reconstruction limit:

```text
resource_limit=max_chunks requested=1025 limit=1024 ... committed_chunks=1022
resource_limit=max_chunks requested=1025 limit=1024 ... committed_chunks=1024
```

Repeated frame rejections retained the valid volume instead of replaying it. Later
frames could still update existing chunks, but new spatial coverage was limited.
Current preferences reported **0.02 m resolution**, 4 m depth limit, noise 9 and
clearing enabled. The fixed replay baseline's 0.04 m test configuration does not
establish coverage at this finer setting. This is a software chunk-budget limit,
not an observed disk-write failure. Post-scan PSS was 642,044 KiB (~627 MiB).

The first UI snapshot said “Scanning · Move slowly”; a later snapshot confirmed
“Paused · Resume when ready” and the committed count remained 227. The next performance/quality
investigation should address resolution-aware memory budgeting/capacity and
rejection backoff/status behavior rather than treating the storage change as a
complete fix for stalled geometry accumulation.
